# 2026-10-29 代码 review 与修复

本轮最初按只读方式审查。随后用户明确要求“发现了就修改”，并指定推送到 `https://github.com/Adversit/dafeiyu_douyin.git`，因此执行修复、回归验证与 Git 发布。没有把该授权当作真实账号验收通过。

## 发现与处理

| 问题 | 触发及影响 | 修复与回归方向 |
| --- | --- | --- |
| P1 积压任务使用旧触发条件 | 旧事件带已知 @，关闭关系开关或新扫描更新后，pending 仍信旧 eligible，可能继续发送 | 刷新 pending 的事件；处理前和生成后按当前记录与配置复核；succeeded/unknown 不重开 |
| P1 历史已回复目标再次进入发布 | 首次补回时，已扫描到本人对某条评论的直接回复，但本地账本为空，仍给该目标再发一次 | 仅用 schema 已确认的直接回复证据回填具体目标；不将整楼封为已处理，不覆盖 unknown |
| P2 回执作者不一致仍算成功 | 作品/楼层一致而发布回执作者为另一账号，旧代码仍返回 verified | 核对 uid/uid_str；错配保留评论 ID，转 unknown；缺作者不算完整验证 |
| P2 语义判定丢失已知其他对象 | 明确回复其他观众的“能教我吗”与关系未知的相同文字，送给模型的上下文相同 | 保留宿主派生关系、直接父消息、匿名且稳定的发言者与消息引用；模型仍不能修改真实目标 |
| P2 线程时间单位混用 | 网页 create_time 为秒，本机写入回复为毫秒；旧回复会排在更新的真实问题前 | 入站归一化为毫秒；线程优先确认的直接祖先与根消息，不用最新兄弟消息代替父链 |
| P2 确定未发送却不可恢复 | 生成期间换号，适配器在发布前拒绝，publish 调用为 0，任务仍成 unknown | 发送前校验和明确未派发标记 definitelyNotSent；只有可能发出的请求进入 unknown |

这些场景先用模拟回包、内存或临时 SQLite 复现，再修复并补测试。真实模型判断准确率和抖音字段语义仍待账号验收；不会将 mock 结果称为现网验证。

历史直接目标的特殊映射仍受 `inboundSchemaConfirmed` 控制：只有该开关启用、`reply_to_reply_id` 显式为 0 且 `reply_id` 与查询根 ID 匹配时，才认为直接回复根楼；缺字段或未确认时保持未知。无法读取、未分页获取或关系尚未确认的历史回复不能凭空变成本地去重证据。

## 成熟方案实际复用程度

核对了固定 SHA 的上游源文件，区分原码保留、端点适配和设计参考：

- ImageX 签名和上传：明确保留上游两个连续相同块，共 111 行；后续适配不改变这两个核心块。

111 行描述逐行相同块，不代表开发工作量或所有语义复用的比例。详细来源及许可证见 [SOURCES.md](SOURCES.md)。

## 去重保证的范围

本地唯一键绑定账号、作品和实际目标评论；发送前持久化 sending；进程恢复后 sending 转为 unknown，不自动重试。历史回填只认有证据的直接目标，不因某楼已有一条本人回复而压掉楼中的其他新回复。

以上防护依赖本地账本保留、单 worker 执行锁和已确认的平台关系字段。没有声称网页轮询绝不漏数据，也没有声称真实模型必定不误判。最终自动验证命令和未验证项见 [VERIFICATION.md](VERIFICATION.md)。
